# Back-office password-reset patterns

**Scope.** Administrator-initiated resets for managed, internal accounts. This is
not research into public self-service recovery. Findings are external evidence,
not ZH-LAO requirements.

## Comparable platforms

| Platform | Administrator control | Temporary secret and first use | Existing access | Audit / delegation lesson |
| --- | --- | --- | --- | --- |
| Microsoft Entra ID | A user needs an appropriate role (at least Password Administrator for the normal reset path). | The console generates a temporary password and requires a change at next sign-in. | Session revocation is a distinct administrator action; it invalidates refresh tokens, while an application-issued session must be revoked by that application. | Separate reset and session-revocation operations in the user experience, but make the latter a default security step and communicate its boundary. [Reset a user's password](https://learn.microsoft.com/en-us/entra/fundamentals/users-reset-password-azure-portal), [Revoke user access](https://learn.microsoft.com/en-us/entra/identity/users/users-revoke-access) |
| AWS IAM | An authorized administrator resets an IAM user's console password. | It supports an autogenerated password, a forced password change at next sign-in, and displays/downloads the credential only during the completion dialog; it cannot be retrieved later. | The reset dialog can revoke active console sessions, forcing immediate use of the new password. | Treat the plaintext password as a one-view secret; record the security action rather than the secret. IAM and STS actions are logged with caller, IP, time, and request details in CloudTrail. [Manage IAM user passwords](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_credentials_passwords_admin-change-user.html), [IAM/STS CloudTrail integration](https://docs.aws.amazon.com/IAM/latest/UserGuide/cloudtrail-integration.html) |
| Google Workspace | Password reset requires the specific reset-password privilege; resetting another administrator requires Super Admin. Privileges can be scoped to organizational units. | Admins can generate a secure password and require the user to change it at their next sign-in; the UI offers copy or delivery to an address the user can currently access. | Password reset alone is insufficient for full containment: admins reset sign-in cookies separately; together they sign the user out of active sessions. Password reset also revokes application-specific passwords. | Enforce least-privilege authorization and protect peer/privileged-account resets. Make session revocation part of the reset transaction rather than relying on operators to remember a separate step. [Reset a user's password](https://support.google.com/a/answer/33319), [Administrator privilege definitions](https://support.google.com/a/answer/1219251) |

## Cross-platform findings

1. **Authorization is explicit and tier-aware.** Reset capability is granted to a
   narrow administrator role, with stronger protection for resetting fellow
   administrators or more-privileged accounts (Entra and Google).
2. **Use a generated, non-recoverable bootstrap secret.** AWS models the safest
   display: generate it, show it only in the immediate completion experience,
   and require a change on first sign-in. Avoid putting it in audit events,
   notification logs, browser history, or later account views.
3. **A reset must terminate existing access.** The industry controls distinguish
   identity-provider refresh-token revocation from application-owned sessions.
   A ZH-LAO flow needs to revoke its own sessions atomically with the password
   change, rather than claim it can invalidate sessions outside its control.
4. **Audit the security event, never the credential.** The audit record should
   identify the acting administrator, target operator, outcome, timestamp,
   correlation/request ID, source context, and session-revocation result.
   AWS's CloudTrail illustrates the useful accountability fields; its logging
   guidance also shows the importance of masking accidentally submitted secrets.
5. **The UI needs a deliberate confirmation and safe handoff.** State that all
   target sessions will end, show the generated temporary password once after
   success, provide a deliberate copy action, and warn the administrator to
   transfer it through an approved channel. Failures must not expose a secret or
   leave a password changed while session invalidation silently failed.

## Implications to validate against local authorities

- Whether the reset permission may act on peer or higher-privilege operators.
- Whether the temporary password has a time expiry in addition to first-use
  enforcement; the compared products differ, so no external default is assumed.
- The exact session store/token boundary and whether password change plus session
  revocation can be one atomic server-side operation.
- The canonical audit-event schema, retention, and access controls.
