# Migration Risk Matrix — 管理端通用数据表增强

| # | Risk | Severity | Detection / trigger | Concrete mitigation |
| --: | --- | :---: | --- | --- |
| 1 | Either target table or migration number `1340` already exists from an untracked change | HIGH | Pre-check finds an object or filename collision | Stop as repository drift; compare the live catalog, migration registry and canonical contract. Do not use `IF NOT EXISTS`, rename around the collision, or overwrite an applied migration. |
| 2 | Candidate DDL drifts from the canonical Content contract | HIGH | Review or `validation.sql` reports a field, constraint, index, or FK mismatch | T005 re-grounds against the canonical Content database page and ADR-028 immediately before adoption; require Content-owner review and fail deployment on any catalog mismatch. |
| 3 | Rollback destroys long-retained task and item history | HIGH | Either table contains at least one row | Prefer application rollback while preserving the additive schema. Permit schema rollback only with explicit Content-owner/database-operator approval and a verified restorable backup; record the incident decision. |
| 4 | Application deploys before schema and fails on missing relations | HIGH | Startup/smoke request returns undefined-table errors | Enforce schema-first deployment and make the successful read-only validation a release prerequisite before enabling task admission or the worker. |
| 5 | A lifecycle or counter update violates the new checks and strands work | MEDIUM | Constraint-violation rate is non-zero in staging or production | Run transition/counter integration tests on a disposable PostgreSQL database before release; use the same transaction for item result and task counters; on production error, stop admission and inspect the safe application path rather than weakening constraints. |
| 6 | Migration waits on catalog locks or contributes to replica lag | MEDIUM | Lock wait >5 seconds or replay lag >30 seconds | Apply during a monitored low-write window with the migration advisory lock; pause rollout at threshold. The change touches only new empty objects, so do not introduce concurrent-index work or existing-table DDL. |
| 7 | An accidental cross-domain FK couples Content to Operations or logical Content/Revision UUIDs | HIGH | Validation detects any FK other than item → task | Keep `requested_by_operator_id`, `content_id`, and `revision_id` as UUID columns without physical FKs; `validation.sql` fails if an unexpected FK appears. |
| 8 | Normal index creation conflicts with zero-downtime expectations | LOW | Review flags a non-concurrent index build | All indexes target tables created empty in the same transaction, so normal creation cannot scan or block writes to existing business tables. Keep them in the atomic migration; do not use `CREATE INDEX CONCURRENTLY` inside the runner transaction. |
| 9 | Migration succeeds but the generated manifest or expected-schema inventory remains stale | HIGH | Backend compatibility check or database audit fails | Treat T005 manifest generation and expected-schema update as part of the implementation change; generate checksums with the repository script and require clean-install plus 1330→1340 upgrade tests. Never hand-edit generated hashes. |
| 10 | Retry/application code leaves stale errors or timestamps that checks reject | MEDIUM | Retry integration test raises a check violation | In the retry transaction, reset only failed items to `queued`, clear error and attempt/completion timestamps, increment `retry_count`, and atomically subtract failed/processed counters before returning the task to `queued`. |
| 11 | A deployment partially registers migration state | HIGH | Schema objects and `v2_schema_migrations` disagree | Run only through the repository runner, which wraps DDL and registry insert in one transaction under an advisory lock. Do not execute `forward.sql` directly in production. |
| 12 | Unbounded future history increases table/index size | MEDIUM | Storage growth or index bloat exceeds the Content capacity budget | Establish table/index size dashboards before feature enablement and capacity alerts owned by Content. Retention is locked as long-term/no cleanup by ADR-028, so scale storage or propose a separately approved retention revision; do not silently delete rows. |
