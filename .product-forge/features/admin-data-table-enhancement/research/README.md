> 研究维度：竞品、UX/UI、代码库；未运行技术栈比较和指标/ROI 分析。

## 执行摘要

成熟管理端将搜索/筛选（改变结果集）、列设置（改变呈现）和已选记录的批量操作（改变对象）明确分离；跨页全选必须从“本页”经显式二次选择升级到“当前查询全部”。仓库已有 TanStack Table、基础客户端 DataTable、加载/空/错误状态、列可见性与两种分页 API 示例，但并没有服务端表格状态或通用批量写入契约。

因此下一阶段不能把竞品交互直接转成开发事项。必须先由 Content 领域确定目标审核实体、允许的动作及状态机、权限/审计、选择范围和查询/分页契约；通用 DataTable 仅能提供与领域无关的呈现和状态管理能力。

## 关键发现

| 维度 | 核心发现 |
| --- | --- |
| 竞品 | Shopify、Linear 等把筛选范围、选中范围和资源相关批量操作清晰关联；这只能作为交互参考。 |
| UX/UI | 应采用“本页全选 → 明确选择当前查询全部”的双阶段模型，并报告批量成功、失败和跳过结果。 |
| 代码库 | 现有 DataTable 为客户端分页；管理端已有 Offset 与游标接口示例，但内容字母列表尚未具备搜索、排序或分页契约。 |
| 约束 | URL 列表状态由 TanStack Router Search Params 所有；权限、业务状态与操作审计始终归属 Owner Domain/Operations。 |

## 建议方向

先把共享 DataTable 扩展设计为同时支持当前客户端数组模式与由页面提供的服务端查询/分页状态；保持领域无关，避免让组件知道“审核”“发布”等动作。页面通过 URL 管理搜索、筛选、排序与分页；每个 Owner Domain 声明可筛选/排序字段、行标识、可用批量动作、权限与结果处理。高风险或不可逆动作采用明确范围和确认，后端返回逐项成功/失败/跳过结果并由 Operations 记录成功的后台操作审计。

## 产品规格需解决的开放问题

1. 第一批接入哪一个 Content 审核实体/页面，而非笼统“所有表格”？
2. 每个批量审核动作的合法状态转换、权限、并发/幂等、原子性与部分失败语义是什么？
3. 选择仅限当前页，还是可显式扩展到当前查询全部？最大数量和数据变化后的失效策略是什么？
4. Content 列表允许哪些搜索字段、筛选项和排序字段；采用 Offset 还是游标分页，并返回哪些元数据？
5. 列可见性是本地偏好、URL 状态还是可保存/共享的视图？导出是否在范围内？

## 风险与红旗

- `未缓解`：不存在被批准的 Content 批量审核 API、权限矩阵或结果契约；不得从 UI 需求反推它们。
- `未缓解`：跨页选择语义未决，直接实现会产生误审核风险。
- `已识别`：ADR-023 冻结统一 API 信封；新接入不能引入第三种响应结构，直接触及旧接口时是否迁移须由契约所有者决定。
