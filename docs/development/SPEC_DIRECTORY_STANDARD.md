# 规格目录组织规范

## 目标

定义 ZH-LAO 项目中所有 Feature 规格文档的统一目录结构，保证不同领域、不同功能可以按照相同方式进行规格开发。

## Feature 规格目录

每个 Feature 必须拥有独立规格目录：

```text
docs/features/

└── 领域名称/

    └── Feature名称/

        ├── 01-需求规格.md
        ├── 02-产品规格.md
        ├── 03-领域设计.md
        ├── 04-架构规格.md
        ├── 05-数据规格.md
        ├── 06-可执行规格.md
        ├── 07-实施规格.md
        ├── 08-伪代码规格.md
        ├── 09-行为规格.md
        └── 10-验收规格.md
```

## 文件编号规则

编号代表生命周期顺序，不代表文档重要程度。

禁止跳过前置阶段直接进入后续阶段。

例如：

不能直接创建：

```text
08-伪代码规格.md
```

而没有：

```text
01-需求规格.md
02-产品规格.md
03-领域设计.md
```

## Feature 总索引

每个 Feature 必须包含：

```text
FEATURE_SPEC_INDEX.md
```

用于记录：

- Feature 基本信息
- 当前规格状态
- 当前阶段
- 下一阶段
- 阻塞问题
- 关联领域
- 关联验收

## 目录规则

领域目录负责业务边界。

Feature 目录负责单个功能能力。

禁止：

- 多个领域共享同一个 Feature 规格目录
- 一个 Feature 横跨多个目录
- 用实现模块目录代替业务 Feature 目录

## 生命周期对应关系

目录顺序必须对应：

```text
需求规格
↓
产品规格
↓
领域设计
↓
架构规格
↓
数据规格
↓
可执行规格
↓
实施规格
↓
伪代码规格
↓
行为规格
↓
验收规格
```

## 说明

该规范用于保证 Spec 开发过程中的文档统一性，使 AI 和开发人员可以通过固定结构理解 Feature 的完整上下文。
