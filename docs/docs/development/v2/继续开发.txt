# 二、当前已知审查发现

开始 IDN-20 时必须优先确认并处理以下两项。

## HIGH-01 — Production runtime provider wiring

当前代码审查发现：

```text
createIdentityHttpDependencies()
```

在没有显式传入 Facebook verifier 时，默认：

```text
FakeFacebookCredentialVerifier(new Map())
```

而：

```text
apps/backend/src/main.ts
```

没有显式传 production Facebook verifier。

这意味着正式运行时会静默使用 Fake verifier。

虽然空 Map 不会形成认证绕过，但违反冻结安全原则：

```text
Fake providers = tests only
Production must never silently use Fake
```

并且导致正式 `/auth/facebook` 实际不可用。

必须修复。

正确原则：

```text
Test:
FakeFacebookCredentialVerifier
FakeOtpDeliveryProvider

Production / normal runtime:
real configured provider
OR
explicit Unavailable provider
```

没有真实 Facebook provider 时：

```text
UnavailableFacebookCredentialVerifier
```

而不是 Fake。

# 四、OTP Runtime Provider 审计

当前正式运行入口使用：

```text
ConsoleOtpDeliveryProvider
```

它虽然不会泄漏 raw OTP，但不会真正发送短信。

必须在 IDN-20 做明确裁决。

如果项目当前尚未进入 Production Provider Integration：

允许保留“未实现真实 SMS provider”作为明确 production-readiness debt。

但 normal runtime 不应伪装成发送成功。

检查现有 `ConsoleOtpDeliveryProvider` 是否：

```text
RequestPhoneOtp returns accepted
but no OTP is actually delivered
```

如果是：

这会造成正式 API 表面成功、实际用户永远收不到 OTP。

因此 Final Gate 前建议修正为：

```text
未配置真实 SMS provider
→ UnavailableOtpDeliveryProvider
→ PROVIDER_UNAVAILABLE / 503
```

而不是 fake-success placeholder。

如果确实存在明确的：

```text
development mode
```

允许 Console provider：

必须由显式配置启用。

例如：

```text
IDENTITY_OTP_PROVIDER=console
```

仅 development。

Production / default：

不得静默 Console-success。
