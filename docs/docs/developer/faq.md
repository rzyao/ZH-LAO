# 开发者常见问题

## 第一次接手项目应该读什么？

先读[产品画像](product)、[用户旅程](journeys)、[能力地图](capabilities)和[交付状态](delivery-status)，再进入对应功能页。需要业务规则时查阅 Reference 下的产品、领域、架构和 ADR；需要执行具体变更时读取对应 `.specify/` 与 `specs/` 工件。

## Spec Kit 能证明功能已经完成吗？

不能。Spec Kit 描述需求、方案和实现任务；功能是否真实完成，必须由代码、测试、CI 和明确的验收证据证明。发现文档、代码或测试之间存在漂移时，应停止扩展范围并报告冲突。

## `active`、`implemented` 和 `complete` 分别代表什么？

功能页的 `portfolio_status: active` 只表示它仍在产品范围内；它不能推出任何交付层已经实现。交付状态应逐层读取 Backend、Admin、Mobile、Integration 和 Acceptance 的证据。阶段或基础设施的 `complete` 也不等于整个用户旅程已经可用。

## 本机怎样查看项目？

第一次运行前需要 Node.js 和 pnpm；后端业务流程还需要 PostgreSQL 及正确的本地环境配置。Windows 启动脚本提供常用入口：

- `双击启动文档.bat`：文档站 `http://127.0.0.1:15172`。
- `双击启动Admin.bat`：运营后台 `http://127.0.0.1:15173`。
- `双击启动移动端.bat`：浏览器或 Android 模拟器中的移动端预览。
- `双击执行数据库迁移.bat`：初始化或升级本地数据库。
- `双击启动后端.bat`：后端服务 `http://127.0.0.1:18080`。

只阅读文档或查看静态页面时，不必启动全部服务；要体验真实数据流程，通常先准备数据库，再启动后端，最后启动 Admin 或移动端。各应用 README 仍是对应运行细节的入口。

## 设计、代码和状态发生冲突时怎么办？

长期业务事实以 Reference canonical 文档为准，产品范围和人类可读状态以本全景为准，执行规格以 `.specify/` 与 `specs/` 为准，真实交付以代码、测试和 CI 为准。迁移时保留的契约/证据快照只用于追溯，不是当前调度权限。

## 为什么不直接恢复旧开发看板？

旧开发目录和旧阅读入口已经退役。旧 Gate、任务清单和阶段报告可能仍有历史价值，但不能作为当前主任务、并行任务或阻塞链；需要历史背景时从 Git 历史恢复，并以当前代码和测试重新核验。
